구매부터 회계까지,
각 업무의 책임을 분명히 나누다

구매·자재관리 프로세스를 RAP으로 구현한 6인 팀 교육 프로젝트입니다. 저는 PM과 최종 발표를 맡아 기준정보부터 구매오더, 입고, 회계전표로 이어지는 데이터 관계와 업무 규칙을 정리했습니다.

교육 프로젝트 · 2026PM · ERD/BO 설계RAP 심화과정 최우수상
PROBLEM → DECISION → EVIDENCE

화면보다 먼저 정한 세 가지 기준

담당자가 자기 업무를 처리하면 다음 단계의 데이터가 이어지도록, 관계와 책임부터 설계했습니다.

문제

여덟 개 비즈니스 오브젝트가 서로 다른 데이터를 소유해 중복과 불일치가 생길 수 있었습니다.

제 역할

PM으로 ERD, BO 간 참조 관계, 공통 검증·서비스 노출 기준을 팀과 정리했습니다.

확인한 결과

구매오더를 입고가 참조하고, 입고 수량 갱신과 회계전표 생성까지 이어지는 흐름을 구현했습니다.

01

테이블을 늘리기 전에 중복과 관계를 다시 봤습니다

처음 설계한 ERD에서 같은 의미의 데이터가 여러 곳에 놓이면, 구매 조건이 바뀔 때 어느 값을 기준으로 삼아야 할지 불분명해집니다.

설계 판단

2차 ERD에서 중복된 마스터를 덜어내고 BO 사이의 키·참조 관계를 재정의했습니다. 구매정보레코드는 헤더와 플랜트별 조건을 분리하고, 구매오더 아이템은 업무 키로 식별했습니다.

팀에 적용한 방식

각 BO가 다른 BO의 데이터를 참조할 경로를 정하고, CDS 계층과 텍스트 연관 관계를 공통 규칙으로 맞췄습니다. 화면과 서비스 구현 전에 데이터 소유권을 확인하도록 했습니다.

02

입고가 수량을 전달하고, 구매오더가 완료를 판단합니다

입고 저장 후 구매오더의 누적 입고수량과 완료 여부가 바뀌어야 합니다. 같은 계산을 두 BO에 두면 완료 기준이 달라질 때 수정 범위가 커집니다.

설계 판단

입고 BO는 입고·취소 수량만 전달하고, 누적 수량 계산과 완료 판정은 그 데이터를 소유한 구매오더 BO의 Action에 맡겼습니다.

얻은 점

업무 규칙의 위치가 명확해졌습니다. 완료 기준을 조정할 때 구매오더의 판단 로직을 먼저 확인하면 되고, 입고 쪽은 전달 역할을 유지할 수 있습니다.

입고 저장 · 취소→수량 전달→구매오더 BO가 누적·완료 판단
03

물류 사실과 회계 처리의 실패를 구분했습니다

입고 저장 시 이동유형과 회계결정코드에 따라 전표가 생성됩니다. 그러나 계정결정에 실패했을 때 이미 발생한 입고를 어떻게 다룰지도 정해야 했습니다.

설계 판단

입고(101)는 재고 차변·GR/IR 대변, 취소(102)는 반대 방향으로 전표를 구성했습니다. 전표 생성 실패가 입고 사실 자체를 지우지 않도록 물류 저장과 회계 처리를 구분했습니다.

운영 관점의 남은 과제

입고가 남고 전표가 누락되면 정합성 관리가 필요합니다. 실무로 확장한다면 실패 내역을 기록하고 담당자가 원인 확인·재처리·대사를 할 수 있는 절차까지 설계해야 합니다.

프로세스를 연결하며 배운 것

교육 프로젝트에서 8개 BO를 하나의 흐름으로 연결했고 팀은 최우수상을 받았습니다. 제게 더 중요한 결과는 업무 규칙을 어디에 두어야 변경과 예외에 대응할 수 있는지 구체적으로 배운 점입니다.

제가 책임진 범위

  • 6인 팀 PM · 일정과 산출물, 최종 발표
  • 2차 ERD의 관계와 키 검토, BO 간 책임 분리
  • CDS 구조·공용 검증·상태 전환 방식을 팀의 공통 기준으로 정리

컨설턴트로 이어가고 싶은 일

요구사항을 기능 목록으로 끝내지 않고, 누가 어떤 데이터를 책임지며 실패가 어디에 남는지까지 질문하겠습니다. FI와 구매 프로세스의 접점에서 현업·개발·운영이 같은 기준으로 일하도록 설계를 구체화하고 싶습니다.
