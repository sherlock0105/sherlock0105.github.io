외화 결산이 끝날 때까지
전표와 업무가 이어지도록

가상의 화장품 제조·유통 기업을 대상으로 한 ERP 구축 교육 프로젝트입니다. 저는 7인 팀 PM과 FI/QM 개발을 맡아 외화평가부터 환입까지의 흐름을 만들고, 여러 모듈이 공유하는 전표 생성 기준을 정리했습니다.

교육 프로젝트 · 2025–2026PM · FI/QM 개발Classic ABAP · Fiori
PROBLEM → DECISION → EVIDENCE

제가 내린 세 가지 설계 판단

구현 항목을 모두 펼치기보다, 업무의 위험과 그에 대한 판단이 드러나는 사례를 골랐습니다.

문제

환율 입력, 월말 평가, 익월 환입, 타 모듈 전표가 서로 다른 지점에서 끊길 수 있었습니다.

제 역할

FI 결산 프로그램 개발과 팀 공용 전표 처리 기준, 일정·통합 테스트를 함께 관리했습니다.

확인한 결과

평가 전 시뮬레이션과 전표 생성 흐름을 구현하고, 연동 변경을 추적할 기준을 정리했습니다.

01

외화평가는 ‘계산’보다 ‘확인과 환입’까지 설계

외화 미결 전표에 환율을 적용하는 것만으로는 결산 업무가 끝나지 않습니다. 평가손익을 확인하고 전표를 생성한 뒤 다음 달에 환입해야 합니다.

설계 판단

환율 API 적재와 전기일 기준 환율 조회를 연결했습니다. 월말 평가 전에는 통화별 변동률을 시뮬레이션하고, 평가손익이 0인 대상은 생성 전에 차단했습니다.

구현과 확인

AR/AP·통화·거래처·전표 순으로 내려가는 화면에서 대상과 금액을 확인한 뒤 평가전표와 익월 환입전표를 생성하도록 구성했습니다. 배치 처리에도 같은 전표 생성 방식을 사용했습니다.

02

모듈마다 다른 전표 호출을 하나의 기준으로

SD·MM·PP 등에서 발생한 업무가 FI 전표로 이어질 때, 팀원마다 환율·채번·차대변 검증을 따로 구현하면 연동 시점마다 결과가 달라질 수 있습니다.

설계 판단

공용 Posting Class를 진입점으로 두고 전표유형에 따라 AR/AP/GL 처리를 나눴습니다. 환율 조회와 번호 채번, 필수값·차대변 검증을 한곳에서 다루도록 정리했습니다.

팀에 적용한 방식

호출 방식과 메시지·검증 규칙을 문서로 공유하고, 모듈 담당자와 통합 테스트 시나리오를 맞췄습니다. 개인 프로그램이 완성되는 것보다 전체 흐름이 이어지는지를 확인했습니다.

SD · MM · PP 등 원천 업무→공용 전표 생성 기준→FI 전표 · 후속 조회
03

청구 조건 변경이 FI 세금계정에 미친 영향 추적

통합 과정에서 SD 청구 조건 변경 후 FI 세금계정이 예상과 다르게 결정되는 이슈가 생겼습니다. 화면의 결과만 수정해서는 다시 발생할 수 있는 문제였습니다.

원인 확인

전표의 세금코드와 청구문서 조건유형을 비교하고, 계정결정 흐름까지 거슬러 올라가 변경이 전표에 미친 영향을 확인했습니다.

이후 기준

모듈 간 설정이나 조건을 바꿀 때 원천문서, 전표, 후속 결산에 어떤 필드와 계정이 영향을 받는지 먼저 점검하도록 팀의 영향 검토 항목을 정리했습니다.
