Architecture

설계 원칙

코드 자체보다 왜 이렇게 짜야 하는지 판단하는 기준을 세우는 데 가장 공을 들였습니다. 8개 BO를 만들며 반복해서 마주친 판단을 원칙 4가지로 정리했고, 이 기준이 아래 각 Business Object의 설계에 그대로 적용되어 있습니다.

01 · 검증은 SQL이 하게 한다
Internal Table LOOP → CDS LEFT OUTER JOIN

처음엔 FOR ALL ENTRIES로 일괄 조회 후 LOOP + READ TABLE로 대조하는 Classic ABAP 방식으로 zcl_a10_check를 통일했습니다. 리뷰에서 "판단 로직 자체를 Internal Table이 아니라 CDS 뷰(SQL)가 하게 해야 한다"는 지적을 받아, 존재 여부·조합 유효성 판단을 CDS LEFT OUTER JOIN 후 매칭 안 되는 것만(JOIN 대상 IS NULL) SQL이 골라내는 방식으로 전면 수정했습니다. SORTED/HASHED 테이블도 습관적으로 쓰지 않고 대량 반복조회가 실제로 증명된 경우에만 예외로 남겼습니다.

02 · Cross-BO는 EML EXECUTE만
"얼마"만 전달, 판단은 상대 BO가

입고(호출하는 쪽)는 구매오더 필드를 직접 UPDATE하지 않습니다. 이미 정의된 액션(receiveQty)을 EML EXECUTE로 호출해 "얼마 입고했다"는 사실만 전달하고, 누적 계산과 완료 판정은 구매오더 스스로 책임집니다. COMMIT ENTITIES는 Behavior Implementation 안에서 호출하면 안 되고(프레임워크가 저장 시퀀스 끝에 자동 처리) 넣지 않는 것으로 확정했습니다. 같은 BO 내부 조회는 IN LOCAL MODE, 다른 BO 호출 시엔 쓰지 않는다는 원칙도 코드 전반에 일관 적용했습니다.

03 · 채번은 PK 성격으로 판단
Early Numbering vs Late Numbering

아이템 순번처럼 헤더 안에서 관리되는 키는 NUMBERING 메서드(Early)로, 회계결정코드처럼 PK 자체가 업무 의미를 가지며 Draft 없이 즉시 저장 확정되는 BO는 Late Numbering으로 나눴습니다. determination on save로 PK 필드를 채우려다 BEHAVIOR_CONTRACT_VIOLATION(EMPTY_UPDATE) 덤프를 겪은 뒤 "PK 필드는 UPDATE로 변경 불가"라는 RAP 제약을 실제로 확인하고 정리한 기준입니다.

04 · Prepare는 안내, Activate가 차단
check_confirm으로 최종 확정 통합

개별 soft validation은 Prepare 단계 실시간 피드백(reported)만 담당하고, 정작 저장을 막는 failed 처리가 빠져 있어 실질적으로 아무것도 막지 못하는 구조가 여러 BO에서 반복됐습니다. 8개 BO 모두에 check_confirm을 신설해 Activate 직전 한 번의 READ로 핵심 필드를 모아 failed 처리를 전담시키고, 메시지 생성은 soft validation에게 남겨 같은 조건이 두 번 메시지를 띄우지 않도록 역할을 분리했습니다.

자재 마스터 (MARA)

자재 마스터 + 자재명(다국어) Composition 구조. Object Page 안에서 언어별 텍스트를 CRUD할 수 있게 자식 엔티티로 붙였습니다. 자재유형별로 사용 가능한 플랜트·저장위치·평가클래스 조합이 다른데, 표준 SAP에는 이 3원 조합을 관리하는 개념 자체가 없어 매핑 테이블을 새로 설계했습니다.

공통 클래스 CDS LEFT OUTER JOIN 리뷰 반영
설계 원칙 변경 이력

원래는 SELECT를 FOR ALL ENTRIES로 일괄 조회한 뒤 LOOP + READ TABLE로 매칭하는 방식으로 통일했습니다. 리뷰에서 "이건 Classic ABAP 방식이고 RAP 방식이 아니다. SORTED/HASHED는 데이터가 많을 때만 쓰는 것이지 습관적으로 쓰면 안 되고, 판단 로직 자체를 Internal Table+LOOP이 아니라 CDS 뷰(SQL)가 하게 해야 한다"는 지적을 받아 원칙을 바꿨습니다. 새 원칙은 CDS 뷰(또는 인라인 itab)를 LEFT OUTER JOIN해서 매칭 안 되는 것만(JOIN 대상 IS NULL) SQL이 직접 골라내게 하는 것입니다. Internal Table 타입도 기본은 STANDARD TABLE(EMPTY KEY)로 통일하고, SORTED/HASHED는 실제로 대량 반복조회가 증명된 경우에만 예외적으로 사용합니다.

EML(READ/MODIFY ENTITIES)도 검토했지만, 이 클래스의 메서드는 전부 "업무 코드값(Lifnr/Matnr/Saknr 등)으로 존재 여부를 찾는" 작업인데 각 BO의 실제 키는 UUID라서 EML의 READ ENTITIES로는 애초에 조회가 불가능합니다(EML은 실제 키를 이미 알고 있을 때만 사용 가능). 이런 값 기반 조회·중복 체크는 CDS 프로젝션 뷰 SELECT가 맞는 방식이라고 결론지었습니다.
