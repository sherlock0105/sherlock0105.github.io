Common Design

공통 설계 원칙

한 번 정한 패턴을 8개 모듈에 동일하게 적용했습니다. 아래 5가지가 모든 Business Object의 기반입니다.

01
CDS 3계층 분리
Base Table → Interface(ZI_) → Root(ZR_) → Projection(ZC_)

분리 기준다른 BO가 Base Table을 직접 참조하면 테이블 구조 변경 시 참조하는 모든 지점을 함께 수정해야 합니다. 외부 참조는 Interface View(ZI_)로만 가능하도록 접근 경로를 강제했습니다.

Interface View (ZI_A10_EKKO) — Text Association 포함
Root View (ZR_) — Composition 및 Draft 대상
Projection View (ZC_) — UI 노출 필드 선별
02
텍스트는 Interface View에 Association으로 재사용
코드성 필드의 텍스트를 사전 정의해 노출

개선 효과메인 Interface View에 Text Association을 정의해 두어, 다수의 Search Help에서 텍스트 조인 로직을 반복 작성하지 않고 재사용할 수 있도록 했습니다.

Interface View에 Text Association 사전 정의
Search Help에서 조인 없이 재사용
03
메시지 상수화
필드명을 단어 단위로 등록하고 공용 문장의 파라미터로 조합

개선 효과「&1는 필수 입력입니다」 형태의 공통 포맷과 필드명 변수를 조합하는 방식으로, 메시지 ID의 무분별한 증가를 막고 유지보수 효율을 높였습니다.

메시지 클래스 — 필드명 단어 단위 등록
공통 문장 포맷 + 파라미터 조합
호출부 — 상수 참조로 통일
04
Draft 단계 검증 — Prepare와 Activate 역할 분리
실시간 피드백과 최종 저장 차단을 나눔

검증 로직 분리개별 Validation은 Prepare 단계에서 실시간 피드백을, Activate 단계의 확인 검증이 최종 저장 차단을 담당하도록 분리했습니다. 동일 오류가 중복 출력되는 것을 방지하고 입력 편의성을 확보했습니다.

Prepare — 입력 중 실시간 피드백
Activate — 최종 저장 차단 전담
05
사용중지 · 해제 Action으로 상태 전환
물리 삭제 대신 상태 플래그를 Action으로만 변경

설계상태 플래그를 read-only로 제어해 Action을 통해서만 변경되도록 했습니다. 중지 사유는 Action 파라미터로 입력받아 저장하므로 변경 이력을 추적할 수 있습니다.

사용중지 Action — 사유 파라미터 입력
상태 플래그 read-only 제어
해제 Action — 상태 복원

매핑 테이블 신규 정의 종속 Search Help Interface View
매핑 테이블 · Interface View 신규 정의

설계일반 CDS View는 고정 조건만 사용할 수 있으나, 101(입고)은 잔량이 남은 품목만, 102(취소)는 입고 이력이 있는 품목만 노출해야 합니다. 요청 시점의 파라미터에 따라 조회 조건을 분기할 수 있도록 커스텀 엔티티로 구성했습니다.

Custom Entity — 파라미터 기반 조회 분기
이동유형에 따라 달라지는 후보 목록
플랜트 · 자재코드 · 창고 자동 매핑

설계Determination으로 값을 산출하고 Side Effects로 화면 갱신 대상을 지정해, 참조 문서 선택과 동시에 관련 필드가 동기화되도록 구현했습니다.

Determination + Side Effects — 참조 선택과 동시 동기화
이동유형에 따라 참조 대상이 달라진다

설계101·102는 구매오더 참조가 필수이며, 311(플랜트이동)·511(무상입고)은 구매오더 없이도 입고할 수 있습니다. 이동유형별로 BO를 분리하지 않고 단일 BO 내에서 분기 처리했고, 이동유형 변경 시 필수 항목과 입력 가능 항목이 함께 전환되도록 화면 제어를 연결했습니다.

이동유형별 필수 항목·입력 가능 항목 전환
입고취소(102) — 입고 문서를 참조하는 설계

설계 근거동일한 구매오더 아이템이 여러 차례 분할 입고될 수 있어, 구매오더만 참조하면 어느 입고 건에 대한 취소인지 특정되지 않습니다. 취소가능수량 산정과 전표 역분개의 기준을 명확히 하기 위해 입고 문서를 참조 대상으로 삼았습니다.

취소 시 입고문서(101) 참조 — 구매오더 아님
입고문서 선택 시 관련 필드 자동 매핑
한 문서 안에서는 이동유형 방향이 같아야 한다

제약 배경입고번호를 이동유형에 따라 4/5/9번대로 구분해 채번하는데, 헤더는 첫 아이템의 이동유형을 기준으로 판단합니다. 한 문서에 방향이 혼재되면 채번 기준이 성립하지 않아 자체 검증으로 단일성을 보장했습니다.

입고·출고 방향 혼재 문서 저장 차단
⑥ ↔ ⑦ 연동 Cross-BO Action

BO 간 연동 — 구매오더 ↔ 입고

입고를 저장하면 구매오더의 입고수량과 완료여부가 갱신됩니다.

Cross-BO Action 책임 분리
계산 책임은 데이터를 소유한 BO에

설계 방향입고 BO는 입고·취소된 수량 정보만 파라미터로 전달하고, 누적 수량 계산과 완료 여부 판정은 구매오더 BO가 Action으로 직접 수행하도록 했습니다. 완료 판정 기준이 변경되어도 입고 로직은 영향을 받지 않습니다.

구매오더 BO의 수량 갱신 Action 선언
입고 저장 시 Action 호출 — 수량만 전달
누적 계산·완료 판정은 구매오더 BO가 수행
⑧ 회계 BKPF / BSEG · 조회 전용

회계전표 (BKPF / BSEG)

입고 저장이 확정된 직후 전표 생성 로직이 호출되어 회계전표가 생성됩니다.

자동 전표 생성 T030 계정 결정 예외 처리 원칙
입고 · 입고취소 시 전표 자동 생성

설계회계결정코드(T030)에서 이동유형별 계정을 조회해 차변·대변 라인을 구성합니다. 101 입고는 자재 계정 차변 / GR-IR 대변, 102 취소는 GR-IR 차변 / 자재 계정 대변으로 역분개됩니다.

T030 조회 후 차변·대변 라인 구성
101 입고 — 자재 차변 / GR-IR 대변
102 취소 — 역분개 전표
전표 생성이 실패해도 입고 저장은 유지된다

설계 근거입고는 이미 발생한 물류 활동이므로 회계 처리 실패를 이유로 저장을 차단하면 현업 업무가 중단됩니다. 전표 생성 실패는 오류로 처리하지 않고, 이후 수기 생성이 가능하도록 여지를 남겼습니다.

기준정보부터 구매·입고·회계까지 8개 모듈을 하나의 프로세스로 연결했습니다.

01
표준에 없는 규칙은
직접 정의
자재유형·플랜트·저장위치 조합처럼 표준에 통제 구조가 없는 규칙은 커스텀 테이블로 정의하고, 검증과 Search Help가 그 정의 하나를 공통 참조하도록 했습니다.
02
입력 순서와 범위를
설계로 강제
공급업체 선택 전 아이템 생성 차단, 자재 기준 플랜트·저장위치 자동 반영과 같이 잘못된 조합이 입력되는 경로 자체를 차단했습니다.
03
계산 책임은
데이터 소유 BO에
입고는 수량 정보만 전달하고 누적·완료 판정은 구매오더 BO가 수행합니다. 판정 기준이 변경되어도 호출하는 쪽은 영향을 받지 않습니다.
04
한 번 정한 패턴을
8개 모듈에 재사용
CDS 계층 구조, Text Association, 메시지 상수화, 검증 단계 분리, 상태 전환 Action을 공통 규칙으로 두고 모든 모듈에 동일하게 적용했습니다.
결과 구매오더를 생성하면 입고에서 참조되고, 입고를 저장하면 구매오더 수량이 갱신되며 회계전표까지 자동 생성됩니다. 담당자는 각 화면에서 자기 업무만 처리하면 되고, 모듈 간 연계는 시스템이 담당합니다.
